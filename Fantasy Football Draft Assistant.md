# Research Report: Building a Static, Claude-Assisted Fantasy Football Draft Assistant

## TL;DR
- **Build it as a pure static HTML/CSS/vanilla-JS (or lightweight React/Vite) single-page app on GitHub Pages, using the "bring-your-own-key" pattern**: Anthropic enabled CORS on 23 August 2024 via the `anthropic-dangerous-direct-browser-access: true` header, so the browser can call Claude directly with a user-supplied key stored in `localStorage` — acceptable for a single-user local tool, though a Cloudflare Worker proxy is the more secure alternative.
- **Use FantasyPros consensus rankings + ADP CSV exports as the static local data source** (columns like `RK, TIERS, PLAYER NAME, TEAM, POS, BYE WEEK, SOS SEASON, ECR VS. ADP` plus `AVG./BEST/WORST/STD.DEV`), and have Claude Code write a parser that normalizes these into a single JSON player pool; embed VORP/value-based-drafting, tier cliffs, positional scarcity, and round-sensitive roster needs into the LLM prompt.
- **Write the spec as a `PROJECT_BRIEF.md` (plus a `CLAUDE.md`) with tightly-scoped sections** — Project Overview, Tech Stack & Constraints, Data Model, File Structure, Feature List, Draft Logic, LLM Prompt Design, and phased Milestones — and let Claude Code plan before coding.

## Key Findings

### 1. Architecture for a client-side-only, GitHub Pages–compatible draft tool
- GitHub Pages serves only static assets and cannot set custom HTTP headers or run server code. There is no backend, so all state and logic must live in the browser.
- Anthropic enabled CORS for its JSON API on 23 August 2024, first surfaced by Simon Willison: "Anthropic have enabled CORS support for their JSON APIs... You can now add the following HTTP request header: `anthropic-dangerous-direct-browser-access: true`." Anthropic named the header "dangerous" deliberately because embedding a key in client code exposes it.
- Two legitimate patterns exist: (a) **Bring-your-own-key** — the app prompts the user for their Anthropic key and stores it in `localStorage`; acceptable for internal/single-user tools. (b) **Lightweight serverless proxy** (Cloudflare Worker, Vercel function) that holds the key server-side and forwards requests; more secure and also solves CORS. Per Cloudflare's official Workers pricing docs, the free plan includes 100,000 requests/day (resetting at 00:00 UTC) and 10 ms CPU time per invocation — far more than a draft needs.
- For this use case (one person, running locally during a live draft), bring-your-own-key stored in `localStorage` is the pragmatic recommendation, with a documented Cloudflare Worker option for users who don't want their key in the browser. The app can even run fully locally (opened from disk or `localhost`) and only be pushed to Pages for convenience.
- Draft state (drafted players, rosters, settings, API key) should persist in `localStorage` so a browser refresh mid-draft doesn't wipe progress. Note the GitHub Pages quirk that `localStorage` is shared per-origin across all repos on `username.github.io`, so keys should be namespaced/prefixed.

### 2. Static/downloadable aggregate ranking data sources and their formats
- **FantasyPros is the best fit.** Per FantasyPros' own API page, it aggregates ECR and ADP from 130+ ranked experts, with tiers and the spread of opinion (best, worst, std-dev) — its homepage phrases this as "advice from 100+ experts." It offers Half-PPR rankings and a consensus ADP, and premium members can export rankings/cheat sheets to Excel/CSV via the Cheat Sheet Creator and Draft Wizard.
- **FantasyPros consensus rankings export columns (verbatim, ALL-CAPS):** `RK` (overall rank), `TIERS`, `PLAYER NAME`, `TEAM`, `POS` (position with embedded positional rank, e.g., `RB1`, `WR12`), `BYE WEEK`, `SOS SEASON` (strength of schedule, 0–5 rating), `ECR VS. ADP`. Expanded expert-consensus exports also include `AVG.`, `BEST`, `WORST`, and `STD.DEV` (spread of expert opinion). The underlying field set is confirmed by independent parsers (the `fantasypros` R package returns `scoring, rank, tier, player, team, pos, pos_rank, bye, best, worst, avg, std_dev, adp, vs_adp`).
- **FantasyPros ADP export columns:** `Rank` (positional), `Overall` (overall ADP rank), `Player Team (Bye)` — a **single combined cell** like `Josh Allen BUF (7)` — then one column **per source site** (varies by active sources; historically `ESPN, Sleeper, NFFC, RTSports, FFC, CBS, Yahoo, BB10`), and `AVG`. There are separate ADP pages per format; ESPN ADP is under PPR scoring and Yahoo ADP is under Half-PPR scoring.
- **Format quirks to handle in the parser:** (1) ADP combines name+team+bye in one cell, and name suffixes like "II" (e.g., `Patrick Mahomes II KC (10)`) complicate splitting; (2) rankings `POS` embeds the position rank (`RB1`) so you must strip trailing digits for the bare position; (3) DST/defenses use position `DST` and are named by team; (4) downloaded CSVs often include title/metadata rows above the header and a footer line (e.g., `ADP Sources: RTSports, BB10`) that must be skipped; (5) header punctuation is exact (`AVG.`, `STD.DEV`); (6) UTF-8 for special characters.
- **Other sources:** ESPN and Yahoo publish cheat sheets primarily as **PDF/print** (not clean CSV), so they're weaker for automated ingestion. Sleeper has **no native rankings/ADP CSV export**, though FantasyPros aggregates Sleeper draft data as one of its ADP sources. Recommendation: standardize on FantasyPros Half-PPR consensus rankings CSV (for tiers/ECR) + FantasyPros ADP CSV (for market pricing), and treat any others as optional secondary inputs the parser can merge by player name.

### 3. Draft logic and strategy concepts to embed in the LLM prompt
- **Value Over Replacement Player (VORP / VBD):** The core concept, introduced to fantasy football by Footballguys co-founder Joe Bryant in 1996 ("I introduced VBD to the fantasy football world back in 1996 when players like Keyshawn Johnson, Eddie George, and Marvin Harrison had yet to play an NFL down"). His definition: "The value of a player is determined not by the number of points he scores. His value is determined by how much he outscores his peers at a particular position." A player's value is his projected points minus the "replacement level" — the last startable player at his position given league size and roster settings. Per Draft Day Authority, "In a 12-team standard fantasy football league, the replacement quarterback is typically defined as QB13... A running back in a league with two RB starters and one FLEX has a replacement level around RB25 or RB37." This is why elite RB/WR generate more surplus value than elite QB despite lower raw totals (the "water–diamond paradox").
- **Positional scarcity:** Positions where production drops off steeply (RB, elite TE) should be prioritized over deep positions (QB, WR depth). This is why QBs "last longer" on the board than raw projections suggest.
- **Tier-based drafting / tier cliffs:** Group players into tiers and track how many remain in the current tier at each position. If a tier is about to empty ("cliff"), that position becomes urgent; if many remain, you can wait and take another position. FantasyPros exports include a `TIERS` column that can drive this directly.
- **Roster construction / round-sensitivity:** Standard 10-team Half-PPR consensus is a "2 RBs through the first 3 rounds, then attack WR value" approach, with alternatives like Hero-RB (one elite RB then hammer WR). QB and TE can usually wait unless an elite tier is about to break; DST and K should be reserved for the final two rounds. The recommendation engine should weight roster needs more heavily as the draft progresses (early = best value available; late = fill required starters and handcuffs).
- **Snake pick math:** For an `N`-team snake, in odd rounds team `t` picks at overall `(round-1)*N + t`; in even rounds at `(round-1)*N + (N - t + 1)`. For a 10-team league, if you pick 5th you pick 5th in odd rounds and 6th in even rounds. The app should precompute all of the user's overall pick numbers and show "picks until your turn."
- **Best available vs. need:** The engine should combine (a) best-player-available by VORP/ECR, (b) the user's positional needs, (c) tier cliffs and position runs, and (d) ADP value (is the player falling relative to ADP?). The strongest open-source example (below) explicitly blends "board value, VORP, need, scarcity, and risk" into safe/balanced/upside modes.

### 4. Prior art / open-source projects for design inspiration
- **`zacharykirby/ai-nfl-fantasy-draft`** — the closest analog: a VORP-based draft engine with live session tracking and an **optional LLM reasoning layer** (via OpenRouter). Key design lessons directly applicable here: keep player facts and draft state **deterministic and auditable**; the model **explains** recommendations but does not own availability or mutate state; the app remains fully usable if the LLM is unavailable (deterministic fallback); send the model a **small bounded "evidence packet" and an available-player allowlist** rather than the whole board; use **structured/validated responses**; and keep the API key server-side. It computes snake-order pick ownership, tier cliffs, recent position runs, and round-sensitive roster needs.
- **`jjti/ff` (ffdraft.app)** — ranks players by Value Over Replacement using ESPN/CBS/NFL projections; good reference for the VORP calculation and cross-source projection merging.
- **`gnmerritt/fantasy-bot`** — jQuery front end that picks best-available by VORP and runs **entirely in the browser** ("everything runs in your browser"); computes positional demand from starter+bench slots × teams. Good static-app precedent.
- **`NateConroy1/fantasy-draft-helper`** — simple offline draft manager for compiling rankings.
- **`pjconnell/Fantasy_Football_Draft_Widget`** (DAsHA) — uses Gaussian KDE to show projection distributions/upside during a live draft; inspiration for surfacing floor/ceiling, not just point estimates.
- General `draft-assistant` GitHub topic shows several static PWAs (e.g., "Static PWA, zero build" Superflex cockpits), confirming the static-app approach is well-trodden.

### 5. Best practices for the spec / project-brief markdown fed to Claude Code
- **Keep it concise and high-signal, then let Claude expand it.** Oversized specs overflow the context/"attention budget." Start with a clear goal and core requirements; use Claude Code's **Plan Mode** (Shift+Tab) to have it explore and produce a detailed plan before writing code (Anthropic's recommended loop is Explore → Plan → Implement → Commit).
- **A `CLAUDE.md` at the project root is auto-loaded every session.** A widely-adopted structure: Project Overview (the "why" in 1–2 sentences), Tech Stack & Constraints (with **exact versions and rejected alternatives** to prevent drift), Architecture, Directory/File Structure, Commands (dev/build/test), Coding Conventions, and Important Rules / "Do Not Touch." Document architecture and data flow, not just the stack.
- **Effective spec sections for scaffolding from scratch:** Goal/Overview; Tech Stack; Data Model (schemas); File Structure; Feature List (as vertical slices that cross data+logic+UI, not horizontal layers); Draft Logic spec; LLM Prompt/Contract spec; Non-Goals/Constraints; and phased Milestones with acceptance criteria. Have Claude write tests and commit as it goes.
- **For the LLM call specifically:** Specify **tool-use / structured outputs** so Claude returns guaranteed-valid JSON (define a tool whose input schema is the recommendation shape and force the call). This is far more reliable than "please return JSON." Include a deterministic fallback. Per Anthropic's official pricing (checked 15 Aug 2026), self-serve model IDs are `claude-haiku-4-5-20251001` ($1/$5 per MTok), `claude-sonnet-5` ($2/$10 — Anthropic made this introductory rate permanent on 11 Aug 2026, cancelling the scheduled $3/$15 step-up), `claude-opus-5` ($5/$25), and `claude-fable-5` ($10/$50); cache hits cost 10% of base input and the Batch API is 50% off. A single draft's worth of calls costs pennies, so Sonnet 5 is a sensible default for recommendation quality with Haiku 4.5 as a cheap fallback.

## Details

### Recommended architecture (concrete)
A single-page static app deployed to GitHub Pages. Recommended stack: **Vite + React + TypeScript** (or plain HTML/JS if the user prefers zero build), Tailwind for fast UI, and `localStorage` for all persistence. No backend. Core modules Claude Code should build:
1. **Data ingestion**: file-input that reads user-downloaded FantasyPros CSVs client-side (via `FileReader` + a CSV parser like PapaParse), normalizing into a canonical player array. Optionally pre-convert CSVs to a checked-in `players.json` for zero-friction loading.
2. **League config**: team count (default 10), the user's draft slot, roster template (QB, 2 RB, 2 WR, TE, FLEX, DST, K + 6 bench = 15 rounds), and scoring (Half-PPR). Precompute snake pick order.
3. **Live draft board**: manual entry UI to record each of the 9 opponents' picks (fast search/typeahead by player name, one tap to mark drafted), plus the user's own picks. Track drafted vs. available and current roster.
4. **Recommendation engine**: on the user's turn, assemble a bounded context (roster, needs, top-N available by ECR/VORP per position, tier state, ADP value, picks-until-next-turn) and call Claude; render the pick plus alternatives and rationale.
5. **Persistence & recovery**: autosave draft state to `localStorage`; provide undo and manual "catch-up" entry.

### The Claude API call
- Header set: `x-api-key`, `anthropic-version`, `content-type: application/json`, and `anthropic-dangerous-direct-browser-access: true`.
- Use a forced tool call for structured output: define a `recommend_pick` tool with a schema like `{ primary_pick: {name, position, reason}, alternatives: [{name, position, reason}], positional_advice: string }` and set `tool_choice` to that tool. Post-validate before rendering; on any failure, fall back to a deterministic best-VORP-available pick.
- Send an **available-player allowlist** so the model cannot recommend a drafted player, and keep the context small (don't dump 300 players — send the top ~10–15 per relevant position).

### Draft-strategy content for the prompt (embed as system context)
Include: the league settings; VORP/value-based-drafting definition and replacement levels for a 10-team Half-PPR league; positional scarcity ordering (RB/elite TE scarce, QB/WR deep); tier-cliff awareness using the `TIERS` column; round-sensitive roster construction (2 RB early then WR value; QB/TE can wait; DST/K last two rounds); ADP value signals; and the instruction to weigh best-available early and needs late.

## Recommendations
**Stage 1 — Write the brief (now).** Produce `PROJECT_BRIEF.md` + `CLAUDE.md` with: Project Overview; Tech Stack & Constraints (pin exact versions; state "static only, GitHub Pages, no backend"); Data Model (canonical player schema derived from the FantasyPros columns above); File Structure; Feature List as vertical slices; Draft Logic spec (snake math, VORP, tiers, roster needs); LLM Contract (headers, tool schema, fallback); and phased Milestones. Keep it tight; instruct Claude Code to use Plan Mode first.

**Stage 2 — Scaffold and load data.** Have Claude build the CSV ingestion + normalization and the league/roster config with the snake-order precomputation. **Benchmark:** you can load a FantasyPros Half-PPR CSV and see a correct, deduped, tier-tagged player pool with bye weeks and ADP.

**Stage 3 — Live draft loop (no LLM yet).** Build manual pick entry, drafted/available tracking, roster view, and a deterministic best-available-by-VORP recommendation. **Benchmark:** you can run a full 15-round mock end-to-end with undo and autosave, and the deterministic pick is sensible.

**Stage 4 — Add Claude.** Wire the bring-your-own-key flow + `localStorage`, the forced-tool-call recommendation, the bounded context/allowlist, and the deterministic fallback. **Benchmark:** on your turn you get a valid JSON recommendation with alternatives and rationale in a few seconds, and it never suggests a drafted player.

**Stage 5 — Harden for draft night.** Add a pre-draft "dry run," a printable emergency cheat sheet fallback, and (optionally) a Cloudflare Worker proxy if you don't want the key in the browser.

**Thresholds that change the plan:** If you'll share the app or host the key beyond your own machine → switch from bring-your-own-key to the Cloudflare Worker proxy. If LLM latency/cost is a problem → default to Haiku 4.5 and cache the system prompt. If FantasyPros export access isn't available → fall back to manually maintained CSV in the same schema, or a free ADP source, since the app only depends on the column contract, not the vendor.

## Caveats
- **API-key exposure is real.** Bring-your-own-key in the browser is fine for a private, single-user, local tool, but the key is visible to anyone with access to that browser/site; Anthropic explicitly flags this. Use the Worker proxy if that matters.
- **Rankings are static snapshots.** Because data is downloaded ahead of time, late-breaking injury/news won't be reflected unless you re-download close to draft day. Refresh CSVs the morning of the draft.
- **FantasyPros CSV/Excel export is a premium feature**, and exact export headers can vary slightly by export type (cheat sheet vs. rankings vs. ADP) and year; the parser should be tolerant (match on normalized header names, skip title/footer rows). A live premium-export file could not be opened directly during research, so treat the exact punctuation of headers as "verify on first download," even though the field set is well-corroborated by multiple independent parsers.
- **LLM recommendations are advisory.** The model can hallucinate or over-weight narrative; keep the deterministic VORP engine as the source of truth and have the LLM explain/adjust rather than decide unilaterally.
- **Pricing/model names evolve.** The Aug 2026 figures cited will drift (note Sonnet 5's introductory rate was recently made permanent); confirm the current model IDs and rates in the Anthropic console before finalizing defaults.
